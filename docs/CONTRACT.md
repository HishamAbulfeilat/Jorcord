# Jorcord API contract (source of truth for server + clients)

Base: `/api/v1`. JSON. Auth: `Authorization: Bearer <accessToken>`. Types live in `@jorcord/shared` (`types.ts`, `protocol.ts`).
Errors: HTTP status + `ApiError {code,message,details?}`. Pagination: `?limit=` (default 50, max 100) with `?before=<id>`/`?after=<id>`; lists of messages return newest-first arrays.
Permissions always enforced server-side via `computePermissions` (shared). Permission values are decimal strings on the wire.
All features are free: LIMITS in `shared/limits.ts` apply to everyone. There is NO payment/Nitro checkout.

## Voice (LiveKit)
POST /voice/token {channelId} -> VoiceToken (permission-checked; room = channelId; metadata carries userId)
Voice state is mirrored through gateway op VOICE_STATE_UPDATE + dispatch VOICE_STATE_UPDATE. Server also exposes LiveKit webhook receiver `/voice/webhook`.
Quality: Opus up to 510kbps stereo + DTX/RED; screenshare/camera up to 3840x2160@60 (simulcast + VP9/AV1 SVC, H264 fallback).

## Gateway
WS /gateway. Server sends HELLO{heartbeatInterval}; client sends IDENTIFY{token} -> DISPATCH READY, then DISPATCH events (see `Events`). Heartbeat op 1/ack 11. RESUME with sessionId+seq replays missed events (buffer ≥ 5 min). Presence/typing via Redis (or in-memory) pub/sub, so multiple server nodes can scale horizontally.

### Gateway intents (bots)
`IDENTIFY {token:"Bot ...", intents?}`. `intents` is a bitfield (`Intents` in `@jorcord/shared`, Discord bit positions): GUILDS 1<<0, GUILD_MEMBERS 1<<1 (privileged), GUILD_EMOJIS_AND_STICKERS 1<<3, GUILD_VOICE_STATES 1<<7, GUILD_PRESENCES 1<<8 (privileged), GUILD_MESSAGES 1<<9, GUILD_MESSAGE_REACTIONS 1<<10, GUILD_MESSAGE_TYPING 1<<11, DIRECT_MESSAGES 1<<12, DIRECT_MESSAGE_REACTIONS 1<<13, DIRECT_MESSAGE_TYPING 1<<14, MESSAGE_CONTENT 1<<15 (privileged), GUILD_SCHEDULED_EVENTS 1<<16, GUILD_MESSAGE_POLLS 1<<24, DIRECT_MESSAGE_POLLS 1<<25.
* Omitted `intents` = legacy unfiltered stream (everything the bot may see, as before). Supplying `intents` (even 0) turns filtering on. User sessions ignore the field.
* Delivered only with the matching intent: GUILDS (guild/channel/role/thread/stage events, `GUILD_CREATE|UPDATE|DELETE`), GUILD_MEMBERS (`MEMBER_ADD|UPDATE|REMOVE`, except events about the bot itself; also `REQUEST_MEMBERS`, which otherwise answers an `ERROR` dispatch `MISSING_INTENT`), GUILD_PRESENCES (`PRESENCE_UPDATE`), GUILD_VOICE_STATES, GUILD_EMOJIS_AND_STICKERS, GUILD_SCHEDULED_EVENTS, and per-scope (guild vs DM channel) messages / reactions / typing / poll votes. Always delivered: `READY`, `RESUMED`, `INTERACTION_*`, `APPLICATION_*`, `USER_UPDATE`, `GUILD_MEMBERS_CHUNK`, `ERROR`.
* Without MESSAGE_CONTENT, `MESSAGE_CREATE|UPDATE` in guild channels arrive with `content: ''`, `embeds: []`, `attachments: []` unless the message is from the bot, mentions it, or is a DM. Without GUILD_MEMBERS, `READY`/`GUILD_CREATE` `members` holds only the bot (`memberCount` is still accurate); without GUILD_PRESENCES `READY.presences` is empty.
* Privileged intents must be enabled by the application owner: `PATCH /applications/:id {privilegedIntents}` (bitfield of the three privileged bits; `Application.privilegedIntents`). Gateway close codes: 4013 unknown intent bits, 4014 privileged intent not enabled. Switching a privileged intent off closes live sessions (4004) so they re-identify.

## Additions (server gap-closing pass)
Users: `GET /users?username=` (exact, case-insensitive; accepts `@name`, `name#0`; blocks => 404) ; `DELETE /users/@me {password,totp?}` (409 `OWNS_GUILDS` while owning servers; anonymises) ; `GET /users/@me/export` (JSON download).
Auth: `POST /auth/verify-email {token}` ; `POST /auth/verify-email/send` (authed) ; `POST /auth/password/forgot {email}` (always 204) ; `POST /auth/password/reset {token,newPassword}` (revokes all sessions). Emailed links: `{PUBLIC_URL}/verify-email?token=` and `{PUBLIC_URL}/reset-password?token=`.
Voice moderation (guild perms MUTE_MEMBERS / DEAFEN_MEMBERS / MOVE_MEMBERS + role hierarchy): `GET /guilds/:id/voice-states` ; `PATCH /guilds/:id/voice-states/:userId {mute?,deaf?}` -> `{userId,serverMute,serverDeaf,voiceState}` ; `POST .../voice-states/:userId/move {channelId}` (client must re-fetch a voice token when its own state moves) ; `DELETE .../voice-states/:userId` (disconnect). Mute/deafen persist per member and survive reconnects.
Stage: `PUT|DELETE /channels/:id/stage/request` (REQUEST_TO_SPEAK) ; `PUT|DELETE /channels/:id/stage/speakers/:userId|@me` (invite = unsuppress needs MUTE_MEMBERS; anyone may step themselves down). `VoiceState.requestToSpeakAt` (ISO|null) is additive.
Webhook execute body accepts `username`, `avatarUrl` (or `avatar_url`) per message.
Gateway: op `REQUEST_MEMBERS` (8) `{guildId,query?|userIds?,limit?,after?,nonce?}` -> dispatch `GUILD_MEMBERS_CHUNK`. Users that lose view access to a channel (overwrite / role / member-role change) receive `CHANNEL_DELETE`; users that gain it receive `CHANNEL_CREATE` (`THREAD_CREATE` for threads). `THREAD_MEMBERS_UPDATE {id,guildId,addedUserIds,removedUserIds}`.
Threads: `GET /channels/:id/threads/active|archived?before&limit` -> `{threads,members,hasMore}` (legacy `GET /channels/:id/threads?archived=` kept) ; `GET /guilds/:id/threads/active` -> `{threads,members}` ; `GET /channels/:id/thread-members` ; `PUT|DELETE /channels/:id/thread-members/:userId|@me` (others need MANAGE_THREADS or thread ownership). Creating a thread, or posting in one, follows it.
Group DMs: `PUT /channels/:id/recipients/:userId` (any participant; friends-or-shared-server rule, blocks, max 10) ; `DELETE /channels/:id/recipients/:userId|@me` (owner removes others; owner leaving transfers ownership).
Search: `GET /channels/:id/messages/search?q&authorId&has&before` (works for DMs) ; `GET /users/@me/messages/search?q=` (all DMs). Postgres uses full-text word-prefix matching.

## Platform pass: applications, bots, commands, interactions, components, polls, events, stages, tags
Everything below is additive. Wire stays camelCase / string enums at `/api/v1`; numeric fields below (interaction types, component types, event status...) follow Discord's public numbering. Types: `packages/shared/src/platform.ts`.

### Errors, rate limits
- Every error body gains `errorCode` (Discord-style number, `ErrorCode` in shared; e.g. 10003 unknown channel, 50013 missing permissions, 50035 invalid form body, 20001/20002 bot/user-only, 40060 interaction already acknowledged, 520000 poll voting blocked). The string `code` is unchanged. Validation failures also carry `errors: { "<dotted.path>": { _errors: [{code,message}] } }`.
- Every `/api/*` response carries `X-RateLimit-Limit|Remaining|Reset|Reset-After|Bucket` (bucket = opaque id per method+route). Limits are per credential per route (+ resource id), plus 50 req/s per credential, 600/min per IP. 429: `{code:'RATE_LIMITED', message, details:{retryAfter}, retry_after (float s), global, errorCode}` with `Retry-After`, `X-RateLimit-Scope` (`user|global`), `X-RateLimit-Global`. 10,000 401/403/429 per 10 min from one IP is a temporary ban (Discord's invalid-request limit).

### Applications and bots
`POST /applications {name,description?,icon?,redirectUris?,botPublic?}` -> 201 `Application` incl. one-time `token` (bot token) and `clientSecret`. `GET /applications` (mine) ; `GET /applications/:id` ; `PATCH /applications/:id {name,description,icon,redirectUris,botPublic,interactionsEndpointUrl}` ; `DELETE /applications/:id` (removes the bot from all guilds) ; `GET /applications/@me` (bot) ; `GET /applications/:id/installs`.
`POST /applications/:id/bot/reset-token` -> `{token}` (old token dead at once, bot gateway sessions closed 4004) ; `POST /applications/:id/reset-secret` -> `{clientSecret}`. Max 25 apps per user. Tokens/secrets are stored as sha256, the interactions private key AES-GCM encrypted; plaintext is never returned again.
Bot auth: `Authorization: Bot <token>` on REST, and `IDENTIFY {token:"Bot <token>"}` on the gateway. Bots get 403 (errorCode 20001) on `/auth/*`, relationships, push, export, `DELETE /users/@me`, `POST /applications`, `POST /interactions`, `/oauth2/authorize`, and cannot join servers by invite (`POST /invites/:code`), discovery join, create servers or boost: bots enter a server only through the OAuth2 install flow. Any request may send `content-type: application/json` with an empty body (treated as `{}`). Bots are ordinary members: their effective permissions come from a managed role (name = app name, position 1, cannot be deleted by hand; removed with the bot).
OAuth2: `GET /oauth2/authorize?clientId&scope=bot applications.commands identify&permissions=N` -> `{application,scopes,permissions,guilds[]}` (guilds the caller can manage). `POST /oauth2/authorize {clientId,scope,permissions?,guildId?,redirectUri?,state?}` (user session): `bot`/`applications.commands` need `guildId` + MANAGE_GUILD, and requested permissions must be a subset of the caller's own (403 `PERMISSION_ESCALATION`); private bots (`botPublic:false`) only by their owner; installs the bot (dispatches `GUILD_CREATE` to the bot, `MEMBER_ADD`/`ROLE_CREATE` to the guild, audit `BOT_ADD`). `identify` needs an exact registered `redirectUri` (https, or http for localhost/127.0.0.1/[::1] only) and returns a single-use 10-min `code`. **PKCE (RFC 7636, S256 only):** send `codeChallenge` (base64url SHA-256, 43 chars) + `codeChallengeMethod:'S256'` to authorize and `codeVerifier` (43-128 chars) to the token endpoint; `plain` is refused, and a code issued with a challenge is useless without the verifier. `applications.commands` on a private bot is owner-only too. `POST /oauth2/token {clientId,clientSecret,grantType:'authorization_code',code,redirectUri}` -> `{accessToken (jco_...),tokenType,expiresIn,scope}` (a redirect mismatch or a wrong `codeVerifier` burns the code) ; `POST /oauth2/token/revoke` ; `GET /oauth2/@me` (Bearer jco_ token; identify -> `{user:{id,username,displayName,avatar,bot}}`). OAuth tokens are not API credentials.

### Application commands
Per application (bot token of that app, or its owner): `GET|POST|PUT /applications/:app/commands`, `GET|PATCH|DELETE /applications/:app/commands/:cid`, and the same under `/applications/:app/guilds/:gid/commands` (guild scope requires the app installed there). `POST` upserts by (type,name) (201 created / 200 updated); `PUT` bulk-overwrites. Body `{type?:1 slash|2 user|3 message, name, description (slash only, 1-100), options?, defaultMemberPermissions? (Jorcord permission bits string), dmPermission?, nsfw?}`. Options: types 1-10 (11 attachment is rejected at invocation), sub commands/groups, required-first, `choices` (<=25, typed), `autocomplete` (exclusive with choices), min/max value/length, `channelTypes`. Limits (Jorcord's own): 100 slash / 15 user / 15 message per scope, 8000 chars, 200 creates/day/guild (errorCode 30032 when over).
Permissions (guild managers on a user session, MANAGE_GUILD + MANAGE_ROLES): `GET /applications/:app/guilds/:gid/commands/permissions`, `GET|PUT .../commands/:cid/permissions {permissions:[{id,type:1 role|2 user|3 channel,permission}]}` (`cid` = app id sets the app-wide default). Evaluation: admins pass; channel deny; user overwrite; role allow/deny; @everyone overwrite; else `defaultMemberPermissions`; always needs USE_SLASH_COMMANDS. Audit `APPLICATION_COMMAND_PERMISSION_UPDATE`.
`GET /guilds/:id/application-commands?channelId=` -> `{commands[],applications[{id,name,icon,botUserId}]}`: what the caller may run (installed apps, permissions applied). Events `APPLICATION_COMMAND_CREATE|UPDATE|DELETE` (guild commands to the guild; a **global** command event goes to every guild the app is installed in, with `guildId: null`, so clients re-read `GET /guilds/:id/application-commands`).

### Interactions
User side (user session only): `POST /interactions` -> 202 `{id}`; bodies by `type`:
`{type:2, channelId, data:{id, options?:[{name,type,value|options}], targetId?}}` command (options re-validated against the stored definition; `targetId` for user/message commands; resolved user/message is sent to the bot) ; `{type:4, ...}` autocomplete (`focused:true` option) ; `{type:3, channelId, messageId, data:{customId, values?}}` component press ; `{type:5, channelId, interactionId, data:{customId, components:[{type:1,components:[{type:4,customId,value}]}]}}` modal submit (once per modal, checked against the modal definition).
Delivery: gateway dispatch `INTERACTION_CREATE` to the bot, or, when `interactionsEndpointUrl` is set, an Ed25519-signed HTTP POST (`X-Signature-Ed25519` hex over `X-Signature-Timestamp + rawBody`, verify with `Application.publicKey`; HTTP 200 JSON body `{type,data}` is the initial response). Setting the URL requires it to answer a signed `{type:1}` PING with `{type:1}`; delivery is SSRF-guarded. The user gets `INTERACTION_FAILED {id,applicationId,channelId}` when the app did not acknowledge within 3 s (token then dead) or is offline.
App side (token = credential, valid 15 min, stored hashed; any mismatch/expiry is 404 errorCode 10062):
`POST /interactions/:id/:token/callback {type,data?}` -> 204. Types: 4 message, 5 deferred message (public placeholder with flag LOADING 128, or ephemeral), 6 deferred update, 7 update component message, 8 autocomplete result `{choices<=25}` (-> user event `INTERACTION_AUTOCOMPLETE_RESULT`), 9 modal (-> user event `INTERACTION_MODAL {interactionId,modal}`). Second response: 400 errorCode 40060. `data`: `{content<=4000, components, flags (64 EPHEMERAL, 4 SUPPRESS_EMBEDS)}`.
`POST /interactions/:id/:token/messages` (followup, max 10; the first one after a deferred response fills the placeholder) ; `GET|PATCH|DELETE /interactions/:id/:token/messages/@original|:mid`. (Discord uses `/webhooks/{app}/{token}`; Jorcord keeps these under `/interactions` because `/webhooks/:id/:token` is the webhook executor.)
Ephemeral responses are stored in `ephemeral_messages`, never in `messages`: delivered only to the invoking user as `MESSAGE_CREATE/UPDATE/DELETE` (flags & 64), absent from history, search, pins and exports; components on them can only be pressed by that user.

### Message components, polls, flags
`Message` gains `components`, `poll`, `flags`, `applicationId`, `interaction {id,type,name,userId}`; `type` gains `poll_result`. `POST /channels/:id/messages` accepts `components` (bots only; 403 errorCode 20002 otherwise), `poll`, `flags` (4 only). `PATCH .../messages/:mid` accepts `content?` and `components?` (owning bot only).
Components: action rows (<=5) of <=5 buttons, or one select. Component `{type, customId, ...}`: 2 button (`style` 1-4 need `customId`; 5 link needs `url` http/https; `label`<=80, `emoji`, `disabled`), 3 string select (`options` 1-25 `{label,value,description?,emoji?,default?}`), 5 user / 6 role / 7 mentionable / 8 channel select, `placeholder`, `minValues`, `maxValues`; 4 text input only inside modals (`label`, `textStyle` 1|2, `minLength`, `maxLength`, `required`, `value`). Unique `customId` per message.
Polls: `poll: {question<=300, answers:[{text<=55, emoji?}] (1-10), durationHours (1-768, default 24), allowMultiselect?}` needs SEND_POLLS in guild channels. `Message.poll = {question,answers:[{id,text,emoji,count,meVoted}],allowMultiselect,layoutType:1,expiry,isFinalized,totalVotes}`. `PUT /channels/:id/polls/:mid/votes {answerIds:[]}` (replaces my votes; [] clears) ; `DELETE .../votes/@me` ; `GET .../polls/:mid/answers/:answerId?after&limit` -> `{users}` ; `POST .../polls/:mid/expire` (author or MANAGE_MESSAGES; audit `POLL_END`). Votes after expiry/finalize: 400 errorCode 520000. At expiry (sweeper) the poll is finalized once and a `poll_result` message (replyTo the poll) is posted. Events `MESSAGE_POLL_VOTE_ADD|REMOVE {userId,channelId,messageId,answerId,count,totalVotes}` (`count` = the answer's new total, `totalVotes` = distinct voters after the change, i.e. the percent base), plus `MESSAGE_UPDATE` on finalize. `MESSAGE_UPDATE` for a poll is a broadcast: its `meVoted` marks are never the viewer's, so clients keep their own marks (from their `PUT .../votes` response) when merging it. Members who are timed out or still pending screening cannot vote (403).

### Scheduled events, stage instances, voice-channel chat
Scheduled events: `GET|POST /guilds/:id/scheduled-events`, `GET|PATCH|DELETE .../:eid`, `GET .../:eid/users?limit&after&withMember`, `PUT|DELETE .../:eid/users/@me` (interested). `ScheduledEvent {id,guildId,channelId,creatorId,name,description,scheduledStartTime,scheduledEndTime,privacyLevel:2,status 1 scheduled|2 active|3 completed|4 canceled,entityType 1 stage|2 voice|3 external,location,image,userCount,interested}`. External: no channel, `location` + end time required. Permissions follow Discord: CREATE_EVENTS (+ VIEW_CHANNEL/CONNECT for voice, + MANAGE_CHANNELS/MUTE/MOVE for stage); modify/delete by creator with CREATE_EVENTS or anyone with MANAGE_EVENTS. Transitions: SCHEDULED->ACTIVE|CANCELED, ACTIVE->COMPLETED; completed/canceled are immutable. Lifecycle sweeper starts events at `scheduledStartTime` and completes them at the end time (ACTIVE without end: after 24 h); a stage event opens/closes a stage instance. Channel-bound events are only visible to people who can see the channel. Events `GUILD_SCHEDULED_EVENT_CREATE|UPDATE|DELETE`, `GUILD_SCHEDULED_EVENT_USER_ADD|REMOVE {guildScheduledEventId,userId,guildId}`. Max 100 upcoming per guild.
Stage instances: `POST /stage-instances {channelId,topic (1-120)}` (409 `STAGE_EXISTS`) ; `GET /stage-instances/:channelId` ; `GET /guilds/:id/stage-instances` ; `PATCH` (topic) ; `DELETE`. Needs MANAGE_CHANNELS+MUTE_MEMBERS+MOVE_MEMBERS in the channel. Empty instances are ended after 60 s. Events `STAGE_INSTANCE_CREATE|UPDATE|DELETE`.
Voice-channel text chat: voice and stage channels take `POST/GET /channels/:id/messages` under SEND_MESSAGES / READ_MESSAGE_HISTORY with normal overwrites (no server change needed; covered by tests).

### Forum tags and thread lifecycle
Forum `Channel` gains `availableTags [{id,name,emoji,moderated}]`, `requireTag`, `defaultAutoArchiveDuration`; threads gain `appliedTags`, `autoArchiveDuration` (60|1440|4320|10080), `locked`, `archiveAt`. `PATCH /channels/:forum {availableTags (<=20, send existing ids to keep them), requireTag, defaultAutoArchiveDuration}` (MANAGE_CHANNELS; audit `FORUM_TAG_UPDATE`; removed tags vanish from posts). `POST /channels/:forum/forum/posts` accepts `appliedTags` (<=5, moderated tags need MANAGE_THREADS) and `autoArchiveDuration`; `POST .../messages/:mid/threads` accepts `autoArchiveDuration`. `PATCH /channels/:thread {autoArchiveDuration, locked, appliedTags, archived}`: `locked` only by MANAGE_THREADS. **Locked semantics (changed):** a locked thread takes no messages from anyone without MANAGE_THREADS, open or archived (403 `THREAD_LOCKED`, errorCode 50083); only they may unarchive it. `locked:false` restores normal behaviour (an archived unlocked thread is revived by the next message). Threads auto-archive after idle time (`THREAD_UPDATE`); any message or unarchive restarts the clock. Deleting a thread emits `THREAD_DELETE {id,guildId,parentId}` (plus the existing `CHANNEL_DELETE`) and audits `THREAD_DELETE`.

### Audit log
`AuditEntry.actionType` (numeric, `AuditActionType` in shared; Discord's value where an equivalent exists) alongside the string `action`; `GET /guilds/:id/audit-logs?actionType=`. New actions: `BOT_ADD`, `MESSAGE_DELETE` (moderator deleting someone else's), `MESSAGE_PIN|UNPIN`, `MEMBER_UPDATE` (nick), `STICKER_UPDATE`, `STAGE_INSTANCE_*`, `GUILD_SCHEDULED_EVENT_*`, `THREAD_DELETE`, `APPLICATION_COMMAND_PERMISSION_UPDATE`, `POLL_END`, `FORUM_TAG_UPDATE`.

### Permissions added (Jorcord bit positions, see `DISCORD_PERMISSION_BITS` for Discord's)
`MANAGE_EVENTS` 38, `CREATE_EVENTS` 39, `SEND_POLLS` 41, `USE_EXTERNAL_APPS` 42. Migration 005 grants SEND_POLLS + USE_EXTERNAL_APPS to existing @everyone roles.

### Discovery join, screening, stickers, themes, status expiry
`POST /discover/guilds/:id/join` (alias `POST /guilds/:id/join`) -> 200 `GuildFull`; 404 unless the guild has `DISCOVERABLE`; same ban / server-limit checks as invites. Guild `PATCH {memberScreening}` (needs a rules channel) toggles feature `MEMBER_SCREENING`: new joiners get `Member.pending=true` and are read-only (VIEW_CHANNEL + READ_MESSAGE_HISTORY only, like a timeout) until `PUT /guilds/:id/members/@me/screening {acceptRules:true}` (emits `MEMBER_UPDATE`); `GET /guilds/:id/screening` -> `{enabled,rulesChannelId,description,pending}`. Gateway `STICKERS_UPDATE {guildId,stickers}` on sticker create/rename/delete. `User.themeColors [#rrggbb,#rrggbb]|null` via `PATCH /users/@me` (public). `customStatus.expiresAt` (ISO, future, <1 year) is enforced server-side: reads as cleared at expiry and the sweeper clears it and broadcasts `PRESENCE_UPDATE`.

Operational: `SWEEP_INTERVAL_MS` (default 10000, 0 disables) drives poll expiry, scheduled events, idle stage cleanup, thread auto-archive, status expiry, interaction pruning. All transitions are atomic UPDATEs, safe on several nodes.

## Social pass (parity)
Inbox: `GET /users/@me/mentions?before&limit(<=50)&guildId&roles=true|false&everyone=true|false` -> `Message[]` newest first: messages that @mention me, one of my roles (`roles`) or @everyone/@here (`everyone`), across my servers and DMs. Re-checked per channel on every call (READ_MESSAGE_HISTORY), never my own messages, never from users I blocked. Mutes are a client concern.
Notes: `GET /users/@me/notes/:userId` (404 when none) ; `PUT /users/@me/notes/:userId {note<=256}` -> 204 (empty/blank deletes) ; the note is also returned as `note` (or null) by `GET /users/:id`, which additionally returns `mutualFriends: User[]` (<=100). Gateway `USER_NOTE_UPDATE {userId,note|null}` goes to the author's own sessions only.
Privacy: `SelfUser.privacy {allowDmsFromServerMembers, messageRequests, showActivity, friendRequests:{everyone,friendsOfFriends,serverMembers}}` (defaults all true; never on other users' objects) set with `PATCH /users/@me {privacy}` (partial, merged server-side). Enforced: `POST /users/@me/channels` and group-DM adds refuse non-friends with 403 `DM_DISABLED` when the target switched DMs off or ignored the caller (friends always pass; an existing DM keeps working); `PUT /users/@me/relationships/:id {friend}` answers 403 `FRIEND_REQUEST_BLOCKED` unless one enabled group matches (everyone / friends-of-friends / shares a server); accepting a request you received is always allowed.
Message requests: a *new* 1:1 DM from a non-friend to someone with `messageRequests` on is a request for the recipient (`dm_participants.request`): invisible until the first message (then `CHANNEL_CREATE` + `MESSAGE_REQUEST_UPDATE {channelId,request:true}`), excluded from push and mention badges, listed in `READY.messageRequests` (channel ids). `POST /channels/:id/accept-request` -> 204 (also: replying accepts; `MESSAGE_REQUEST_UPDATE request:false`) ; `POST /channels/:id/ignore-request` -> 204 (recipient only, 400 unless still a request): deletes the conversation for both (`CHANNEL_DELETE`) and the sender can no longer open a DM to the ignorer (403 `DM_DISABLED`).
Forwarding: `POST /channels/:id/messages {forward:{channelId,messageId}}` (users only; nothing else in the body; needs READ_MESSAGE_HISTORY on the source, SEND_MESSAGES (+ATTACH_FILES when the original has files) on the target; 20/min) creates a message with `forward: {content,attachments,embeds,createdAt,editedAt,sourceGuildId,sourceChannelId,sourceMessageId}` — a snapshot (original author omitted, no pings, survives deleting the original). Forwarding a forward keeps the first origin. Forwarded messages cannot be edited.
Saved for later (private): `PUT|DELETE /users/@me/saved/:channelId/:messageId` -> 204 (needs read access; max 250; PUT is idempotent) ; `GET /users/@me/saved/ids` -> `Id[]` ; `GET /users/@me/saved?limit(<=100)&offset` -> `Message[]` newest-saved first, access re-checked per channel (unreadable ones are skipped, not removed). Rows vanish with their message. Gateway `SAVED_UPDATE {channelId,messageId,saved}` to the owner.
Reminders (private): `POST /users/@me/reminders {channelId,messageId,inSeconds(10..1y) | remindAt(ISO)}` -> 201 `Reminder {id,remindAt,firedAt,message}` (max 100 pending) ; `GET /users/@me/reminders` (pending + fired in the last 7 days) ; `DELETE /users/@me/reminders/:id` -> 204 (owner only). The sweeper marks due ones fired once, sends gateway `REMINDER_DUE: Reminder` and, when the user has no gateway session, a push (`kind:'reminder'`). Rows vanish with their message; delivery re-checks read access.
Age gate: `SelfUser.ageConfirmed` ; `POST /users/@me/age-confirm {confirm:true}` -> 204 (self-attested 18+, stored as `users.age_confirmed_at`, `USER_UPDATE` to own sessions) ; `DELETE /users/@me/age-confirm` -> 204. Until confirmed, users get 403 `AGE_RESTRICTED` on message list/post/pins/channel-search of nsfw server channels (threads inherit the parent's flag); guild-wide search omits them. Bots and DMs are exempt. The web client shows an interstitial and a Privacy & Safety switch.
AutoMod depth: `AutoModRule.trigger` gains `keyword_preset`; rules gain `presets ('profanity'|'sexual_content'|'slurs')[]`, `allowList[]` (phrases removed before matching), `mentionLimit` (1-50, default 5), `exemptChannels[]` (threads inherit the parent), `timeoutSeconds` (10..7d, default 60), `customMessage` (<=150, returned as the 400 `AUTOMOD_BLOCKED` message). Preset words match whole words, accent- and leet-insensitively (`5h1t`); custom keywords stay substring matches. Managers (MANAGE_GUILD) stay exempt.

## Parity pass 2
Types: `packages/shared/src/parity.ts`. Everything is free for everyone; limits live in `LIMITS`.

### Soundboard
`SoundboardSound {id,guildId,name,emoji,volume 0..1,url,creatorId,createdAt}`. `GET /guilds/:id/soundboard-sounds` (members) ; `POST` `{name 2-32,url,emoji?,volume?}` / `PATCH .../:soundId {name?,emoji?,volume?}` / `DELETE` (MANAGE_EMOJIS; audit `SOUNDBOARD_SOUND_CREATE|UPDATE|DELETE`). `url` must be the caller's own `POST /uploads` audio file (`audio/*`, <= `LIMITS.maxSoundBytes` 1 MB, 413 otherwise; external URLs refused); max `LIMITS.maxSoundsPerServer` 48 (400 `MAX_SOUNDS`). Gateway `SOUNDBOARD_SOUNDS_UPDATE {guildId,sounds}` to the guild on every change.
Playing: `POST /channels/:voiceChannelId/send-soundboard-sound {soundId}` -> 204. Needs CONNECT + `USE_SOUNDBOARD` in that channel, the caller connected to it (400 `NOT_IN_VOICE`), not server-muted/suppressed/self-deafened (403 `MUTED`); the sound may come from any server the caller is in. 8 per 10 s. Delivered as gateway `VOICE_CHANNEL_EFFECT_SEND {guildId,channelId,userId,sound}` to the users currently in that voice channel only; each client plays it locally, which is also where the global and per-person "mute soundboard" switches live (client prefs `soundboardMuted`, `soundboardMutedUsers`, `soundboardVolume`). No LiveKit track is published, so voice reconnect is untouched.

### Rich presence / activities
`Activity {type 'playing'|'streaming'|'listening'|'watching'|'competing', name<=128, details?<=128, state?<=128, url? (streaming, http/https), startedAt (ISO), applicationId?, largeImage?, smallImage?}`, at most `MAX_ACTIVITIES` (5). `PUT /users/@me/activities {activities}` replaces my list (-> `{activities}`; `startedAt` defaults to now and is clamped to [now-24h, now]; 30/min) ; `GET` ; `DELETE` -> 204. Works for user sessions and **bot tokens** (a bot's own presence; `Bot.setActivity()` in `@jorcord/bot-sdk`). The gateway op `PRESENCE_UPDATE` (3) also takes `{presence?, activities?}`.
Delivery: `PRESENCE_UPDATE` gains `activities` (empty when offline/invisible or when the owner turned sharing off), `READY.presences[]` entries carry `activities`, `GET /users/:id` returns `activities` (always your own). Activities are transient: cleared when the user's last gateway session ends. Privacy: `privacy.showActivity=false` hides them from everybody but yourself and re-broadcasts at once. Bots receive them with the GUILD_PRESENCES intent like any presence event.
Web: member list ("Playing Chess"), friends list, profile card (details + elapsed), Privacy & Safety > Activity (switch + manual editor).

### Cosmetics: avatar decorations, profile effects, name plates, server tags
Free catalog of original CSS art, ids in `@jorcord/shared` (`AVATAR_DECORATIONS` aurora|sunset|neon|frost|ember|wreath|halo|pixel, `PROFILE_EFFECTS` sparkles|snowfall|confetti|rain|fireflies|bubbles, `NAME_PLATES` sunrise|ocean|forest|nebula|gold|mono, `TAG_BADGES` 12 icons). `User` (public, so it rides on every user object and `USER_UPDATE`) gains `avatarDecoration`, `profileEffect`, `namePlate` (ids or null) and `serverTag {guildId,tag,badge}|null`. `PATCH /users/@me {avatarDecoration?, profileEffect?, namePlate?, serverTagGuildId?}`: unknown ids -> 400; `serverTagGuildId` needs membership and a tagged server (400), `null` drops it.
`Guild` gains `tag` (3-4 `[A-Za-z0-9]`) and `tagBadge`; `PATCH /guilds/:id {tag?, tagBadge?}` (MANAGE_GUILD, 400 on bad values). A changed/removed tag is propagated to every wearer (`USER_UPDATE` to the guild); leaving, being kicked/banned or deleting the server clears the wearer's tag (`users.server_tag` is denormalised JSON). Web: Profile settings pickers with live preview, Server Settings > Server Tag, `Avatar` renders the decoration everywhere (CSS in `cosmetics.css`), tag chips in the member list, messages and profile, name plates behind names, effects on the profile banner.

### Safety Setup: verification levels, explicit-media filter, raid protection
`Guild` gains `verificationLevel 0-4`, `explicitFilter 0-2`, `defaultNotifications 'all'|'mentions'` (default `mentions`) and `invitesPausedUntil` (ISO, only while active). Managers (MANAGE_GUILD): `GET /guilds/:id/safety` -> `GuildSafety {verificationLevel, explicitFilter, defaultNotifications, raidProtection {enabled,maxJoins 3-100,windowSeconds 10-600,lockMinutes 5-1440}, invitesPausedUntil, checklist[{id,done}], score}` ; `PATCH /guilds/:id/safety` (any subset, plus `pauseInvites: true|false` = 24 h pause / resume; audit `SAFETY_UPDATE`, `GUILD_UPDATE` event) ; `POST /guilds/:id/safety/preset {preset:'basic'|'recommended'|'strict'}`.
Enforced server-side: **verification level** (1 verified email; 2 + account > 5 min; 3 + member > 10 min; 4 + verified email and account > 7 days, since Jorcord has no phone numbers) gates messages, reactions and new threads/forum posts with 403 `VERIFICATION_REQUIRED`; exempt: owner, bots, anyone with a role, MANAGE_GUILD / MANAGE_MESSAGES / MODERATE_MEMBERS. **Explicit-media filter** (no image classifier ships): attachments of covered authors (1 = members without roles, 2 = everyone but the owner/bots) that are images/videos in channels that are not `nsfw` are stored with `spoiler: true`, i.e. blurred until clicked. **Raid protection**: after each join, `maxJoins` joins (owner and bots excluded) inside `windowSeconds` pause invites and Discovery joins for `lockMinutes` (atomic UPDATE, audit `RAID_DETECTED`, `GUILD_UPDATE`); joins then fail with 403 `INVITES_PAUSED` until it lapses or a manager resumes. **Default notifications** `all`: members with no own server level get push notifications for every message (clients treat it as their level until they choose one). Web: Server Settings > Safety Setup.

### Server onboarding (questions) and hide muted channels
`Onboarding {enabled, defaultChannelIds[], prompts:[{id,title<=100,singleSelect,required,options:[{id,title<=50,description?,emoji?,channelIds[],roleIds[]}]}], responses?}`; `OnboardingResponse {optionIds,channelIds,completedAt}`. Limits: 5 prompts, 12 options each. `enabled` is mirrored as guild feature `ONBOARDING` (so `GUILD_UPDATE` tells clients).
`GET /guilds/:id/onboarding` (members; `responses` = my answers or null; channel ids the caller cannot view are removed for non-managers) ; `PUT /guilds/:id/onboarding {enabled?, defaultChannelIds?, prompts?}` (MANAGE_GUILD; `prompts` replaces the list, ids of existing prompts/options are kept when sent; channels must exist and not be categories/threads; handing out roles needs MANAGE_ROLES, the role strictly below your top role, no bot roles/@everyone and no permission bits you lack: 403 `ESCALATION`; audit `ONBOARDING_UPDATE`).
`PUT /guilds/:id/onboarding/responses {optionIds}` (members, replaces earlier answers; 400 on unknown options, more than one answer to a single-select or a missing required answer): grants the roles of the chosen options and removes option-managed roles of the unchosen ones (roles given by hand are never touched), stores the channels of the chosen options, emits `MEMBER_UPDATE` (and `CHANNEL_CREATE|DELETE` when role changes alter visibility) and returns the response.
Opt-in channels = channels referenced by an option but not in `defaultChannelIds`. Hiding them is presentation, not a permission boundary: once a member answered, the web sidebar shows default channels, other channels no option mentions, and the member's chosen ones, with a "Browse Channels" toggle for the rest. Newcomers are asked once on join (web modal "Channels & Roles", re-openable from the server menu). **Hide Muted Channels** is a per-server client preference (server menu): muted channels are hidden from the sidebar except the open one.

### Announcement channels: follow + crosspost
`ChannelFollow {id,sourceChannelId,targetChannelId,targetGuildId,createdAt, source?{channelName,guildId,guildName,guildIcon}, target?{channelName,guildId,guildName}}`. `POST /channels/:announcementId/followers {webhookChannelId}` -> 201 (also `{channelId, webhookId}` for Discord-shaped clients): the source must be an `announcement` channel the caller can read (member of its server, or a public channel of a `DISCOVERABLE` server, otherwise 404), the target a text/announcement channel where the caller has MANAGE_WEBHOOKS (not the source itself, 409 `ALREADY_FOLLOWING`, max `MAX_FOLLOWERS_PER_CHANNEL` 25 per source, audit `CHANNEL_FOLLOW_CREATE`). `GET /channels/:id/followers` (announcement side, MANAGE_WEBHOOKS) ; `GET /channels/:id/follows` (following side, MANAGE_WEBHOOKS) ; `DELETE /follows/:id` -> 204 (MANAGE_WEBHOOKS on either channel). Follows vanish with either channel.
`POST /channels/:announcementId/messages/:mid/crosspost` -> updated `Message` (author with SEND_MESSAGES or MANAGE_MESSAGES; plain/reply messages only; 10 per hour per channel; 400 `ALREADY_CROSSPOSTED`): sets flag `CROSSPOSTED` (1) on the original (`MESSAGE_UPDATE`) and creates a copy in every following channel (author = the original author, flag `IS_CROSSPOST` (2), `Message.crosspost {guildId,guildName,channelId,channelName,messageId}`, attachments kept, `<@id>`/`<@&id>` become plain `@someone`/`@role` and `@everyone`/`@here` are broken up, so a published message never pings the receiving server). Copies cannot be published again. Web: "Follow Channel" in the header/menu of an announcement channel, "Publish" message action, origin line on copies, Channel Settings > Integrations lists both directions.

### Profile connections
Jorcord does not talk to third-party OAuth providers, so a connection is a **self-declared link with optional proof of control**. `GET /connections/providers` (`github twitch youtube x reddit steam spotify bluesky mastodon website`; `CONNECTION_PROVIDERS` in shared holds each handle pattern and URL builder: the server builds the URL from a validated handle, only `website` takes a full `https://` link without credentials, so a profile cannot link anywhere unexpected). `GET /users/@me/connections` -> `Connection[] {id,type,name,handle,url,verified,visible,createdAt,verifyCode}` ; `POST {type,handle,visible?}` -> 201 (409 `ALREADY_CONNECTED`, 400 bad handle, max `MAX_CONNECTIONS` 20, users only) ; `PATCH /users/@me/connections/:id {visible}` ; `DELETE` (own only). Verification: put `verifyCode` (`jorcord-verify=<18 hex>`) anywhere on the linked page, then `POST /users/@me/connections/:id/verify` -> the server fetches the URL with the SSRF guard (public addresses only, <= 1.5 MB, 3 redirects) and, when the code is present, sets `verified:true`; otherwise 422 `VERIFICATION_FAILED` (message names the code and URL). `GET /users/:id` gains `connections: [{type,name,url,verified}]` (only `visible` ones, verified first). Web: User Settings > Connections, chips with a verified badge on the profile card (`rel="noopener noreferrer nofollow"`).

### Multi-account switcher (web client only, no server change)
The browser keeps the active session in `jorcord.auth.v1` and the other signed-in accounts of the same server in `jorcord.accounts.v1` (`{id,username,displayName,avatar,access,refresh,server,addedAt}`; refresh tokens rotate, so the active account's copy is re-synced on every token change). Same threat model as the single stored session: anyone with access to the browser profile can use it, "Log Out" or "Remove" revokes the account's session server-side (`POST /auth/logout` with its own token). Switching swaps the stored tokens and reloads the app so no store, cache or gateway state of one account can reach another. UI: User Settings > My Account > Accounts (Switch, Remove, Add Account), "Switch Accounts" in the status menu, `/login?add=1` (login stays reachable while signed in; abandoning it loses nothing). Logging out of one account continues with another saved one.
