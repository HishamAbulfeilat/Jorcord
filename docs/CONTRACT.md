# Jorcord API contract (source of truth for server + clients)

Base: `/api/v1`. JSON. Auth: `Authorization: Bearer <accessToken>`. Types live in `@jorcord/shared` (`types.ts`, `protocol.ts`).
Errors: HTTP status + `ApiError {code,message,details?}`. Pagination: `?limit=` (default 50, max 100) with `?before=<id>`/`?after=<id>`; lists of messages return newest-first arrays.
Permissions always enforced server-side via `computePermissions` (shared). Permission values are decimal strings on the wire.
All features are free: LIMITS in `shared/limits.ts` apply to everyone. There is NO payment/Nitro checkout.

## Messages
GET /channels/:id/messages?limit&before&after&around ; POST /channels/:id/messages (JSON or multipart with files[])
PATCH/DELETE /channels/:id/messages/:mid ; POST /channels/:id/messages/bulk-delete
`POST /channels/:id/messages` accepts `allowedMentions {parse?:('users'|'roles'|'everyone'|'replied_user')[], users?:Id[], roles?:Id[]}` (max 100 ids each). Omitted = default behaviour: every parsed mention pings. When present it **overrides** default pings: only `parse` entries ping (users / roles / @everyone/@here / the reply's author), while the explicit `users`/`roles` id lists permit pings for ids actually mentioned in the content **in addition to** `parse`. Mentions still render/highlight as usual (the `Message.mentions` / `mentionRoles` / `mentionEveryone` arrays are unaffected); only notification badges are filtered. DM recipients always collect their badge (they are recipients, not parsed mentions). The field is echoed back as `Message.allowedMentions`.

## Files

## Voice (LiveKit)
POST /voice/token {channelId} -> VoiceToken (permission-checked; room = channelId; metadata carries userId)
Voice state is mirrored through gateway op VOICE_STATE_UPDATE + dispatch VOICE_STATE_UPDATE. Server also exposes LiveKit webhook receiver `/voice/webhook`.
Quality: Opus up to 510kbps stereo + DTX/RED; screenshare/camera up to 3840x2160@60 (simulcast + VP9/AV1 SVC, H264 fallback).

## Gateway
WS /gateway. Server sends HELLO{heartbeatInterval}; client sends IDENTIFY{token} -> DISPATCH READY, then DISPATCH events (see `Events`). Heartbeat op 1/ack 11. RESUME with sessionId+seq replays missed events (buffer ≥ 5 min). Presence/typing via Redis (or in-memory) pub/sub, so multiple server nodes can scale horizontally.

### Gateway intents (bots)
`IDENTIFY {token:"Bot ...", intents?}`. `intents` is a bitfield (`Intents` in `@jorcord/shared`, Discord bit positions): GUILDS 1<<0, GUILD_MEMBERS 1<<1 (privileged), GUILD_EMOJIS_AND_STICKERS 1<<3, GUILD_VOICE_STATES 1<<7, GUILD_PRESENCES 1<<8 (privileged), GUILD_MESSAGES 1<<9, GUILD_MESSAGE_REACTIONS 1<<10, GUILD_MESSAGE_TYPING 1<<11, DIRECT_MESSAGES 1<<12, DIRECT_MESSAGE_REACTIONS 1<<13, DIRECT_MESSAGE_TYPING 1<<14, MESSAGE_CONTENT 1<<15 (privileged), GUILD_SCHEDULED_EVENTS 1<<16, GUILD_MESSAGE_POLLS 1<<24, DIRECT_MESSAGE_POLLS 1<<25.
* Omitted `intents` = legacy unfiltered stream (everything the bot may see, as before). Supplying `intents` (even 0) turns filtering on. User sessions ignore the field.
* Delivered only with the matching intent: GUILDS (guild/channel/role/thread/stage events, `GUILD_CREATE|UPDATE|DELETE`), GUILD_MEMBERS (`MEMBER_ADD|UPDATE|REMOVE`, except events about the bot itself; also `REQUEST_MEMBERS`, which otherwise answers an `ERROR` dispatch `MISSING_INTENT`), GUILD_PRESENCES (`PRESENCE_UPDATE`), GUILD_VOICE_STATES, GUILD_EMOJIS_AND_STICKERS, GUILD_SCHEDULED_EVENTS, and per-scope (guild vs DM channel) messages / reactions / typing / poll votes. Always delivered: `READY`, `RESUMED`, `INTERACTION_*`, `APPLICATION_*`, `USER_UPDATE`, `GUILD_MEMBERS_CHUNK`, `ERROR`.
* Without MESSAGE_CONTENT, `MESSAGE_CREATE|UPDATE` in guild channels arrive with `content: ''`, `embeds: []`, `attachments: []` unless the message is from the bot, mentions it, or is a DM. Without GUILD_MEMBERS, `READY`/`GUILD_CREATE` `members` holds only the bot (`memberCount` is still accurate); without GUILD_PRESENCES `READY.presences` is empty.
* Privileged intents must be enabled by the application owner: `PATCH /applications/:id {privilegedIntents}` (bitfield of the three privileged bits; `Application.privilegedIntents`). Gateway close codes: 4013 unknown intent bits, 4014 privileged intent not enabled. Switching a privileged intent off closes live sessions (4004) so they re-identify.

## Additions (server gap-closing pass)
Users: `GET /users?username=` (exact, case-insensitive; accepts `@name`, `name#0`; blocks => 404) ; `DELETE /users/@me {password,totp?}` (409 `OWNS_GUILDS` while owning servers; 202 `{deletionDueAt,graceDays}`, see "Account deletion grace period") ; `GET /users/@me/export` (JSON download).
Auth: `POST /auth/verify-email {token}` ; `POST /auth/verify-email/send` (authed) ; `POST /auth/password/forgot {email}` (always 204) ; `POST /auth/password/reset/validate {token}` -> `{valid}` (does not consume the token) ; `POST /auth/password/reset {token,newPassword}` (revokes all sessions and emails a change notice). Emailed links: `{PUBLIC_URL}/verify-email?token=` and `{PUBLIC_URL}/reset-password?token=`. Account emails are sent as HTML with a plain-text alternative.
Voice moderation (guild perms MUTE_MEMBERS / DEAFEN_MEMBERS / MOVE_MEMBERS + role hierarchy): `GET /guilds/:id/voice-states` ; `PATCH /guilds/:id/voice-states/:userId {mute?,deaf?}` -> `{userId,serverMute,serverDeaf,voiceState}` ; `POST .../voice-states/:userId/move {channelId}` (client must re-fetch a voice token when its own state moves) ; `DELETE .../voice-states/:userId` (disconnect). Mute/deafen persist per member and survive reconnects.
Stage: `PUT|DELETE /channels/:id/stage/request` (REQUEST_TO_SPEAK) ; `PUT|DELETE /channels/:id/stage/speakers/:userId|@me` (invite = unsuppress needs MUTE_MEMBERS; anyone may step themselves down). `VoiceState.requestToSpeakAt` (ISO|null) is additive.
Webhook execute body accepts `username`, `avatarUrl` (or `avatar_url`) per message, plus `embeds` and `components` (same validation as bots via `lib/embeds` / `lib/components`; `content` may be omitted when at least one of content, embeds or components is present).
Webhooks full API: `GET /guilds/:id/webhooks` (MANAGE_WEBHOOKS) lists every webhook of the server. Tokenless management by webhook id (Discord-shape) with MANAGE_WEBHOOKS on the webhook's channel (and on the destination channel when moving): `GET /webhooks/:webhookId` (no token in the DTO), `PATCH` `{name?, avatar? (null clears), channelId?}` (audit `WEBHOOK_UPDATE`), `DELETE` (audit `WEBHOOK_DELETE`). With the token as the credential (no user auth): `GET /webhooks/:id/:token`, same `PATCH`, `DELETE`, and webhook messages `GET|PATCH|DELETE /webhooks/:id/:token/messages/:mid` (only messages authored by that webhook, in its channel or one of its threads; PATCH accepts `{content}` and recomputes mentions; PATCH/DELETE rate limits 15/10s). Token PATCH/DELETE answers the full DTO {id,guildId,channelId,name,avatar,token,url}. Execute `POST /webhooks/:id/:token` gained `threadId` in the body (must be a thread/post child of the webhook channel) and the `wait` query param: `?wait=true` returns the created `Message` with 200, otherwise 204. Token edits/deletes broadcast `MESSAGE_UPDATE`/`MESSAGE_DELETE`. Webhook create/update/delete (by id or token) broadcast guild `WEBHOOKS_UPDATE {guildId,channelId}`.
Gateway: op `REQUEST_MEMBERS` (8) `{guildId,query?|userIds?,limit?,after?,nonce?}` -> dispatch `GUILD_MEMBERS_CHUNK`. Users that lose view access to a channel (overwrite / role / member-role change) receive `CHANNEL_DELETE`; users that gain it receive `CHANNEL_CREATE` (`THREAD_CREATE` for threads). `THREAD_MEMBERS_UPDATE {id,guildId,addedUserIds,removedUserIds}`.
Threads: `GET /channels/:id/threads/active|archived?before&limit` -> `{threads,members,hasMore}` (legacy `GET /channels/:id/threads?archived=` kept) ; `GET /guilds/:id/threads/active` -> `{threads,members}` ; `GET /channels/:id/thread-members` ; `PUT|DELETE /channels/:id/thread-members/:userId|@me` (others need MANAGE_THREADS or thread ownership). Creating a thread, or posting in one, follows it.
Group DMs: `PUT /channels/:id/recipients/:userId` (any participant; friends-or-shared-server rule, blocks, max 10) ; `DELETE /channels/:id/recipients/:userId|@me` (owner removes others; owner leaving transfers ownership).
Search: `GET /channels/:id/messages/search?q&authorId&has&before` (works for DMs) ; `GET /users/@me/messages/search?q=` (all DMs). Postgres uses full-text word-prefix matching.

## Platform pass: applications, bots, commands, interactions, components, polls, events, stages, tags
Everything below is additive. Wire stays camelCase / string enums at `/api/v1`; numeric fields below (interaction types, component types, event status...) follow Discord's public numbering. Types: `packages/shared/src/platform.ts`.

### Errors, rate limits
- Every error body gains `errorCode` (Discord-style number, `ErrorCode` in shared; e.g. 10003 unknown channel, 50013 missing permissions, 50035 invalid form body, 20001/20002 bot/user-only, 40060 interaction already acknowledged, 520000 poll voting blocked). The string `code` is unchanged. Validation failures also carry `errors: { "<dotted.path>": { _errors: [{code,message}] } }`.
- Every `/api/*` response carries `X-RateLimit-Limit|Remaining|Reset|Reset-After|Bucket` (bucket = opaque id per method+route). Limits are per credential per route (+ resource id), plus 50 req/s per credential, 600/min per IP. 429: `{code:'RATE_LIMITED', message, details:{retryAfter}, retry_after (float s), global, errorCode}` with `Retry-After`, `X-RateLimit-Scope` (`user|global`), `X-RateLimit-Global`. 10,000 401/403/429 per 10 min from one IP is a temporary ban (Discord's invalid-request limit).

### Applications and bots
`POST /applications {name,description?,icon?,redirectUris?,botPublic?}` -> 201 `Application` incl. one-time `token` (bot token) and `clientSecret`. `GET /applications` (mine) ; `GET /applications/:id` ; `PATCH /applications/:id {name,description,icon,redirectUris,botPublic,interactionsEndpointUrl}` ; `DELETE /applications/:id` (removes the bot from all guilds) ; `GET /applications/@me` (bot) ; `GET /applications/:id/installs`.
`POST /applications/:id/bot/reset-token` -> `{token}` (old token dead at once, bot gateway sessions closed 4004) ; `POST /applications/:id/reset-secret` -> `{clientSecret}`. Max 25 apps per user. Tokens/secrets are stored as sha256, the interactions private key AES-GCM encrypted; plaintext is never returned again.
Bot auth: `Authorization: Bot <token>` on REST, and `IDENTIFY {token:"Bot <token>"}` on the gateway. Bots get 403 (errorCode 20001) on `/auth/*`, relationships, push, export, `DELETE /users/@me`, `POST /applications`, `POST /interactions`, `/oauth2/authorize`, and cannot join servers by invite (`POST /invites/:code`), discovery join, create servers or boost: bots enter a server only through the OAuth2 install flow. Any request may send `content-type: application/json` with an empty body (treated as `{}`). Bots are ordinary members: their effective permissions come from a managed role (name = app name, position 1, cannot be deleted by hand; removed with the bot).
OAuth2: `GET /oauth2/authorize?clientId&scope=bot applications.commands identify&permissions=N` -> `{application,scopes,permissions,guilds[]}` (guilds the caller can manage). `POST /oauth2/authorize {clientId,scope,permissions?,guildId?,redirectUri?,state?}` (user session): `bot`/`applications.commands` need `guildId` + MANAGE_GUILD, and requested permissions must be a subset of the caller's own (403 `PERMISSION_ESCALATION`); private bots (`botPublic:false`) only by their owner; installs the bot (dispatches `GUILD_CREATE` to the bot, `MEMBER_ADD`/`ROLE_CREATE` to the guild, audit `BOT_ADD`). `identify` needs an exact registered `redirectUri` (https, or http for localhost/127.0.0.1/[::1] only) and returns a single-use 10-min `code`. **PKCE (RFC 7636, S256 only):** send `codeChallenge` (base64url SHA-256, 43 chars) + `codeChallengeMethod:'S256'` to authorize and `codeVerifier` (43-128 chars) to the token endpoint; `plain` is refused, and a code issued with a challenge is useless without the verifier. `applications.commands` on a private bot is owner-only too. `POST /oauth2/token {clientId,clientSecret,grantType:'authorization_code',code,redirectUri}` -> `{accessToken (jco_...),tokenType,expiresIn,scope}` (a redirect mismatch or a wrong `codeVerifier` burns the code) ; `POST /oauth2/token/revoke` ; `GET /oauth2/@me` (Bearer jco_ token; identify -> `{user:{id,username,displayName,avatar,bot}}`). OAuth tokens are not API credentials.

### Application commands
Per application (bot token of that app, or its owner): `GET|POST|PUT /applications/:app/commands`, `GET|PATCH|DELETE /applications/:app/commands/:cid`, and the same under `/applications/:app/guilds/:gid/commands` (guild scope requires the app installed there). `POST` upserts by (type,name) (201 created / 200 updated); `PUT` bulk-overwrites. Body `{type?:1 slash|2 user|3 message, name, description (slash only, 1-100), options?, defaultMemberPermissions? (Jorcord permission bits string), dmPermission?, nsfw?}`. Options: types 1-10 (11 attachment is rejected at invocation), sub commands/groups, required-first, `choices` (<=25, typed), `autocomplete` (exclusive with choices), min/max value/length, `channelTypes`. Limits (Jorcord's own): 100 slash / 15 user / 15 message per scope, 8000 chars, 200 creates/day/guild (errorCode 30032 when over).
Permissions (guild managers on a user session, MANAGE_GUILD + MANAGE_ROLES): `GET /applications/:app/guilds/:gid/commands/permissions`, `GET|PUT .../commands/:cid/permissions {permissions:[{id,type:1 role|2 user|3 channel,permission}]}` (`cid` = app id sets the app-wide default). Evaluation: admins pass; channel deny; user overwrite; role allow/deny; @everyone overwrite; else `defaultMemberPermissions`; always needs USE_SLASH_COMMANDS. Audit `APPLICATION_COMMAND_PERMISSION_UPDATE`.
`GET /guilds/:id/application-commands?channelId=` -> `{commands[],applications[{id,name,icon,botUserId}]}`: what the caller may run (installed apps, permissions applied). Events `APPLICATION_COMMAND_CREATE|UPDATE|DELETE` (guild commands to the guild; a **global** command event goes to every guild the app is installed in, with `guildId: null`, so clients re-read `GET /guilds/:id/application-commands`).

### Interactions
User side (user session only): `POST /interactions` -> 202 `{id}`; bodies by `type`:
`{type:2, channelId, data:{id, options?:[{name,type,value|options}], targetId?}}` command (options re-validated against the stored definition; `targetId` for user/message commands; resolved user/message is sent to the bot) ; `{type:4, ...}` autocomplete (`focused:true` option) ; `{type:3, channelId, messageId, data:{customId, values?}}` component press ; `{type:5, channelId, interactionId, data:{customId, components:[{type:1,components:[{type:4,customId,value}]}]}}` modal submit (once per modal, checked against the modal definition).
Delivery: gateway dispatch `INTERACTION_CREATE` to the bot, or, when `interactionsEndpointUrl` is set, an Ed25519-signed HTTP POST (`X-Signature-Ed25519` hex over `X-Signature-Timestamp + rawBody`, verify with `Application.publicKey`; HTTP 200 JSON body `{type,data}` is the initial response). Setting the URL requires it to answer a signed `{type:1}` PING with `{type:1}`; delivery is SSRF-guarded. The user gets `INTERACTION_FAILED {id,applicationId,channelId}` when the app did not acknowledge within 3 s (token then dead) or is offline.
App side (token = credential, valid 15 min, stored hashed; any mismatch/expiry is 404 errorCode 10062):
`POST /interactions/:id/:token/callback {type,data?}` -> 204. Types: 4 message, 5 deferred message (public placeholder with flag LOADING 128, or ephemeral), 6 deferred update, 7 update component message, 8 autocomplete result `{choices<=25}` (-> user event `INTERACTION_AUTOCOMPLETE_RESULT`), 9 modal (-> user event `INTERACTION_MODAL {interactionId,modal}`). Second response: 400 errorCode 40060. `data`: `{content<=4000, components, flags (64 EPHEMERAL, 4 SUPPRESS_EMBEDS)}`.
`POST /interactions/:id/:token/messages` (followup, max 10; the first one after a deferred response fills the placeholder) ; `GET|PATCH|DELETE /interactions/:id/:token/messages/@original|:mid`. (Discord uses `/webhooks/{app}/{token}`; Jorcord keeps these under `/interactions` because `/webhooks/:id/:token` is the webhook executor.)
Ephemeral responses are stored in `ephemeral_messages`, never in `messages`: delivered only to the invoking user as `MESSAGE_CREATE/UPDATE/DELETE` (flags & 64), absent from history, search, pins and exports; components on them can only be pressed by that user.

### Message components, polls, flags
`Message` gains `components`, `poll`, `flags`, `applicationId`, `interaction {id,type,name,userId}`; `type` gains `poll_result`. `POST /channels/:id/messages` accepts `components` (bots only; 403 errorCode 20002 otherwise), `embeds` (bots only, same 403; validated by `lib/embeds`: 1-10 embeds of `type:'rich'`, title ≤256, description ≤4096, ≤25 fields with name ≤256 + value ≤1024, footer ≤2048, author ≤256, absolute http(s) `url` on embeds and their image/thumbnail fields, every embed needs title/description/image/fields, 6000 chars total across embeds — 400 `INVALID_EMBEDS` / errorCode 50035 otherwise), `poll`, `flags` (4 SUPPRESS_EMBEDS | 4096 `@silent` = no push notifications, badges still happen). `PATCH .../messages/:mid` accepts `content?` and `components?` (owning bot only).
Components: action rows (<=5) of <=5 buttons, or one select. Component `{type, customId, ...}`: 2 button (`style` 1-4 need `customId`; 5 link needs `url` http/https; `label`<=80, `emoji`, `disabled`), 3 string select (`options` 1-25 `{label,value,description?,emoji?,default?}`), 5 user / 6 role / 7 mentionable / 8 channel select, `placeholder`, `minValues`, `maxValues`; 4 text input only inside modals (`label`, `textStyle` 1|2, `minLength`, `maxLength`, `required`, `value`). Unique `customId` per message.
Polls: `poll: {question<=300, answers:[{text<=55, emoji?}] (1-10), durationHours (1-768, default 24), allowMultiselect?}` needs SEND_POLLS in guild channels. `Message.poll = {question,answers:[{id,text,emoji,count,meVoted}],allowMultiselect,layoutType:1,expiry,isFinalized,totalVotes}`. `PUT /channels/:id/polls/:mid/votes {answerIds:[]}` (replaces my votes; [] clears) ; `DELETE .../votes/@me` ; `GET .../polls/:mid/answers/:answerId?after&limit` -> `{users}` ; `POST .../polls/:mid/expire` (author or MANAGE_MESSAGES; audit `POLL_END`). Votes after expiry/finalize: 400 errorCode 520000. At expiry (sweeper) the poll is finalized once and a `poll_result` message (replyTo the poll) is posted. Events `MESSAGE_POLL_VOTE_ADD|REMOVE {userId,channelId,messageId,answerId,count,totalVotes}` (`count` = the answer's new total, `totalVotes` = distinct voters after the change, i.e. the percent base), plus `MESSAGE_UPDATE` on finalize. `MESSAGE_UPDATE` for a poll is a broadcast: its `meVoted` marks are never the viewer's, so clients keep their own marks (from their `PUT .../votes` response) when merging it. Members who are timed out or still pending screening cannot vote (403).

### Scheduled events, stage instances, voice-channel chat
Scheduled events: `GET|POST /guilds/:id/scheduled-events`, `GET|PATCH|DELETE .../:eid`, `GET .../:eid/users?limit&after&withMember`, `PUT|DELETE .../:eid/users/@me` (interested). `ScheduledEvent {id,guildId,channelId,creatorId,name,description,scheduledStartTime,scheduledEndTime,privacyLevel:2,status 1 scheduled|2 active|3 completed|4 canceled,entityType 1 stage|2 voice|3 external,location,image,userCount,interested}`. External: no channel, `location` + end time required. Permissions follow Discord: CREATE_EVENTS (+ VIEW_CHANNEL/CONNECT for voice, + MANAGE_CHANNELS/MUTE/MOVE for stage); modify/delete by creator with CREATE_EVENTS or anyone with MANAGE_EVENTS. Transitions: SCHEDULED->ACTIVE|CANCELED, ACTIVE->COMPLETED; completed/canceled are immutable. Lifecycle sweeper starts events at `scheduledStartTime` and completes them at the end time (ACTIVE without end: after 24 h); a stage event opens/closes a stage instance. Channel-bound events are only visible to people who can see the channel. Events `GUILD_SCHEDULED_EVENT_CREATE|UPDATE|DELETE`, `GUILD_SCHEDULED_EVENT_USER_ADD|REMOVE {guildScheduledEventId,userId,guildId}`. Max 100 upcoming per guild.
Stage instances: `POST /stage-instances {channelId,topic (1-120)}` (409 `STAGE_EXISTS`) ; `GET /stage-instances/:channelId` ; `GET /guilds/:id/stage-instances` ; `PATCH` (topic) ; `DELETE`. Needs MANAGE_CHANNELS+MUTE_MEMBERS+MOVE_MEMBERS in the channel. Empty instances are ended after 60 s. Events `STAGE_INSTANCE_CREATE|UPDATE|DELETE`.
Voice-channel text chat: voice and stage channels take `POST/GET /channels/:id/messages` under SEND_MESSAGES / READ_MESSAGE_HISTORY with normal overwrites (no server change needed; covered by tests).

### Forum tags and thread lifecycle
Forum `Channel` gains `availableTags [{id,name,emoji,moderated}]`, `requireTag`, `defaultAutoArchiveDuration`; threads gain `appliedTags`, `autoArchiveDuration` (60|1440|4320|10080), `locked`, `archiveAt`. `PATCH /channels/:forum {availableTags (<=20, send existing ids to keep them), requireTag, defaultAutoArchiveDuration}` (MANAGE_CHANNELS; audit `FORUM_TAG_UPDATE`; removed tags vanish from posts). `POST /channels/:forum/forum/posts` accepts `appliedTags` (<=5, moderated tags need MANAGE_THREADS) and `autoArchiveDuration`; `POST .../messages/:mid/threads` accepts `autoArchiveDuration`. `PATCH /channels/:thread {autoArchiveDuration, locked, appliedTags, archived}`: `locked` only by MANAGE_THREADS. **Locked semantics (changed):** a locked thread takes no messages from anyone without MANAGE_THREADS, open or archived (403 `THREAD_LOCKED`, errorCode 50083); only they may unarchive it. `locked:false` restores normal behaviour (an archived unlocked thread is revived by the next message). Threads auto-archive after idle time (`THREAD_UPDATE`); any message or unarchive restarts the clock. Deleting a thread emits `THREAD_DELETE {id,guildId,parentId}` (plus the existing `CHANNEL_DELETE`) and audits `THREAD_DELETE`.

### Audit log
`AuditEntry.actionType` (numeric, `AuditActionType` in shared; Discord's value where an equivalent exists) alongside the string `action`; `GET /guilds/:id/audit-logs?actionType=`. ### Permissions added (Jorcord bit positions, see `DISCORD_PERMISSION_BITS` for Discord's)

### AutoMod v3 (alert channel, regex, more triggers, multi-action, test mode)
`AutoModRule` gains `actions[]` (`block|timeout|alert|warn`, all run; `block`, `timeout` and `warn` stop the message, an `alert`-only rule lets it through; `action` stays as the first entry and is still accepted on write), `alertChannelId` (a text/announcement channel of the same server, else 400), `regexPatterns[]` (<=10, <=100 chars each), `testMode` and `options {spamCount 2-30, spamSeconds 2-60, capsPercent 50-100, capsMinLength 5-200, repeatLimit 5-100}`. At most 50 rules per server (400 `LIMIT_REACHED`).
**Regex safety**: patterns run on a built-in linear-time NFA engine (`apps/server/src/lib/saferegex.ts`), never on V8's backtracking `RegExp`, so a hostile pattern cannot stall the server. Supported: literals, `.`, classes, `\d \w \s \b \B`, `^ $`, groups, `|`, `* + ? {m,n}` (case-insensitive, input clipped to 4000 chars). **Alerts**: each hit posts a rich embed (`title "AutoMod: <rule>"`, description = the message (500 chars), fields User / Channel / Action) in the alert channel as an "AutoMod" webhook-style message (authored by the built-in bot user "AutoMod" (id `1000000000000000001`, never a member), never pings), flood-limited to 30/min per server. `warn` writes a `mod_warnings` row (`source "automod"`). `testMode` rules take no action: the hit is posted (prefixed `[Test]`) and audited as `AUTOMOD_TEST` (146). Members with MANAGE_GUILD are exempt from rules, so use the dry run below to try them.
`POST /guilds/:id/automod/test {content<=4000, mentionCount?}` (MANAGE_GUILD, 30/min) -> `[{ruleId,name,trigger,enabled,testMode,actions,matched,evaluated}]`; no side effects (`spam` is `evaluated:false`: it needs history).

`GET /guilds/:id/boosts` (members) -> `BoostSummary {count, level, perks, nextLevel, boostsToNext, myBoosts, boosters[{user,boosts,since}], settings{announce, boosterRole, boosterRoleId}}`. `POST /guilds/:id/boosts {count?: 1-10}` -> 201 `Guild` (30 requests/h/user); `DELETE /guilds/:id/boosts` takes back your newest boost -> `BoostSummary` (404 when you have none). `PATCH /guilds/:id/boosts/settings {announce?, boosterRole?}` (MANAGE_GUILD; audit `BOOST_UPDATE`).
**Booster role**: the first boost creates a hoisted, permissionless pink "Server Booster" role (`roles.managed_kind = 'booster'`, `ROLE_CREATE`) and grants it (`MEMBER_UPDATE`); the member's last boost removes it. Managed roles (`booster`, `linked`) cannot be added, removed (member PATCH keeps them whatever the client sends), deleted, handed out by onboarding, or copied into templates; `boosterRole:false` deletes the role (`ROLE_DELETE`) and `true` recreates it for current boosters. `Member.boostingSince` (ISO or null) drives the badge. **Announcements**: with `announce` on and a system channel set, each boost posts a `type:"boost"` message whose `content` is `""`, `"xN"` (N boosts at once) or `"level:N"` (the boost reached level N); `GUILD_UPDATE` follows every change.

### Linked roles
A manager (MANAGE_ROLES) attaches `criteria` (AND, 1-5) to an existing role; the server grants the role to members who meet all of them and removes it when they stop. `LinkedCriterion`: `{type:"account_age_days"|"join_age_days", value 0-3650}`, `{type:"message_count", value 1-1e6}` (normal messages in this server), `{type:"connection", provider?}` (a **verified** profile connection, see CONNECTION_PROVIDERS), `{type:"app_metadata", appId, key, op:">="|"<="|"="|"!=", value:int|bool}` (the app must be installed here and have declared `key` with a matching type). Max 10 linked roles per server. A linked role gets `roles.managed_kind = "linked"`: it cannot be added or removed by hand (member PATCH, onboarding), only by the server; unlinking keeps the role and its holders and makes it ordinary again. Creating one needs the role to be below the actor's top role and carry no permission they lack (`ESCALATION`); `@everyone`, bot and booster roles are refused.
`GET /guilds/:id/linked-roles` (members) -> `LinkedRoleView[] {id, guildId, roleId, description, criteria, role:{name,color}, holders, progress:[{met,current}] (the caller's own standing), granted}` ; `POST` `{roleId, description?, criteria}` -> 201 ; `PATCH /:lid` `{description?, criteria?}` ; `DELETE /:lid` -> 204 (audit `LINKED_ROLE_CREATE|UPDATE|DELETE`) ; `POST .../refresh` (anyone: re-check myself, 12/min) -> views ; `POST .../sync` (MANAGE_ROLES, 2/min per server) -> `{checked, changed}` (up to 5000 members) ; `GET .../apps` (MANAGE_ROLES) -> `RoleMetadataApp[]` for the editor. Gateway: `LINKED_ROLES_UPDATE {guildId}` when the configuration changes (refetch); grants and revocations arrive as `MEMBER_UPDATE`. Evaluation runs on join, on the member's messages (at most once a minute per member), when a connection is verified, when an app reports values, on refresh/sync, and a sweeper re-checks age criteria (300 members per server every 10 minutes).
**Bot API** (bot token only, 403 for users): `PUT /applications/@me/role-metadata [{key /^[a-z0-9_]{1,50}$/, name, description?, type:"integer"|"boolean"}]` (<=5 fields, 10/min) declares what the app can report ; `GET` returns it. `PUT /applications/@me/users/:userId/role-metadata {values:{key:int|bool}}` (300/min) sets a member's values (400 on undeclared key or wrong type; 404 unless the user shares a server with the app) and re-evaluates them at once ; `GET` / `DELETE` (204) likewise. An app can only influence criteria that name its own `appId`.

### App Directory
Owners opt in with `PATCH /applications/:id {directoryListed, directoryCategory (moderation|music|games|utility|fun|social|productivity|community|other), directorySummary<=140, directoryTags<=5 (/^[a-z0-9][a-z0-9-]{1,19}$/), directoryPermissions (suggested bits)}`; listing needs `botPublic`, a description >= 10 chars and a summary >= 10 chars, and switching the bot private unlists it. `Application.directory {listed, category, summary, tags, permissions}`. Read side (any signed-in user, 60/min): `GET /directory/apps?q&category&sort=popular|new&limit<=50&offset` -> `{items: DirectoryApp[], total}` (`DirectoryApp {id,name,summary,description,icon,botUserId,category,tags,installs,permissions,listedAt}`; `q` matches name, summary, description and tags with wildcards escaped; no owner, secrets or endpoints are exposed) ; `GET /directory/apps/:id` (404 when not listed) ; `GET /directory/categories` -> `[{id,name,count}]`. "Add to Server" reuses the OAuth2 add-bot flow: `/oauth2/authorize?client_id=ID&scope=bot applications.commands&permissions=BITS` (installer needs MANAGE_GUILD and cannot grant more than they hold). Third-party Twitch/YouTube guild integrations are intentionally not implemented, see `PARITY.md`.

### Moderation tools (Mod View, warnings, notes, bulk, prune, export)
Permissions: reading Mod View / warnings needs any of KICK_MEMBERS, BAN_MEMBERS, MODERATE_MEMBERS, MANAGE_GUILD; warning and noting need MODERATE_MEMBERS; every action on a member respects the role hierarchy (the owner and members above the actor are refused or skipped).
`GET /guilds/:id/members/:userId/mod-view` (120/min) -> `ModView {user, isMember, joinedAt, accountCreatedAt, roles, timeoutUntil, banned, flags, counts{timeouts,bans,kicks,warnings,automodHits24h}, history[{action,moderatorId,reason,createdAt}], warnings[], notes[], mutualGuilds[{id,name}] (only servers the viewer is also in), messages7d}`; 404 for someone never seen in the server. **Safety flags** (`SAFETY_FLAGS`): `new_account` (< 7 days), `raid_joined` (`members.raid_flagged`, set on everyone who joined inside the window when raid protection trips), `spam_suspect` (>= 3 AutoMod hits in 24 h), `dm_restricted` (privacy: no DMs from server members). Recent messages come from the normal search (`GET /guilds/:id/messages/search?authorId=`), which already filters by what the caller may see.
**Warnings**: `GET|POST /guilds/:id/members/:userId/warnings {reason<=500}` (POST -> 201 `ModWarning {id,guildId,userId,moderatorId (null = AutoMod),reason,source:"manual"|"automod",ruleId,createdAt}`; 30/min; not yourself, bots or the owner), `DELETE /guilds/:id/warnings/:wid` (204); audit `MEMBER_WARN` / `MEMBER_WARN_DELETE`. The warned member alone receives gateway `MOD_WARNING {guildId, guildName, reason, createdAt}`. AutoMod's `warn` action writes the same table. The web composer's `/warn @member reason` calls this endpoint instead of posting a message.
**Notes** (moderators only, never shown to the member): `POST /guilds/:id/members/:userId/notes {note<=1000}` (<= 25 per member, 400 `LIMIT_REACHED`), `DELETE /guilds/:id/notes/:nid` (author or MANAGE_GUILD); audit `MOD_NOTE_UPDATE`.
**Bulk**: `POST /guilds/:id/moderation/bulk {action:"ban"|"kick", userIds?<=200, filter?{joinedWithinMinutes<=10080, noRoles, accountYoungerThanDays<=365, raidFlagged}, reason?, dryRun (default true)}` -> `{dryRun, action, matched, affected, skipped[{userId,reason}], users[]}`. Needs BAN_MEMBERS / KICK_MEMBERS; ids or at least one filter are required (never "everyone"); at most 200 targets per call; ban accepts ids of people who already left, kick needs members; skipped: yourself, the owner, higher-ranked members, unknown users, already banned. Rate limit: 3 executions and 20 previews per minute per server. One `MEMBER_BULK_BAN|KICK` audit entry lists the ids.
**Prune**: `POST /guilds/:id/prune {days 1-30, includeRoles?[], dryRun (default true)}` (KICK_MEMBERS) -> `{dryRun, days, count, removed, remaining}`. Candidates joined more than `days` ago, posted no normal message in `days`, are not bots, and hold no role except those in `includeRoles`; hierarchy applies; at most 1000 are removed per run (`remaining` says to run again); 2 runs/min. Audit `MEMBER_PRUNE`.
**Export**: `GET /guilds/:id/mod-log.csv?from&to&all=true&limit` (VIEW_AUDIT_LOG, 5/min) -> `text/csv` attachment (UTF-8 BOM, CRLF), columns `id,time,action,actor_id,actor_name,target_id,target_name,reason,details`; moderation actions only unless `all=true`; up to 10,000 rows; cells starting with `= + - @` get a leading `'` so spreadsheets never run them.

## Phase A additions (permission split, gradient roles, welcome screen, account deletion)

### Split-out permissions (052)
`PIN_MESSAGES` 1<<44, `BYPASS_SLOWMODE` 1<<45, `USE_EXTERNAL_STICKERS` 1<<46 (Discord positions 51, 52, 37 in `DISCORD_PERMISSION_BITS`). Enforced server side:
* `PUT|DELETE /channels/:id/pins/:mid` need `PIN_MESSAGES` in server channels (`MANAGE_MESSAGES` alone is no longer enough). In DMs every participant may still pin.
* Slowmode (`429 SLOWMODE`, `retry-after`) applies to everyone except holders of `BYPASS_SLOWMODE` (owner and ADMINISTRATOR implicitly). `MANAGE_MESSAGES` / `MANAGE_CHANNELS` no longer bypass it by themselves.
* `stickerIds` on `POST /channels/:id/messages`: stickers of the channel's own server always work. A sticker of another server is kept only when the sender has `USE_EXTERNAL_STICKERS` in the channel **and** is a member of the sticker's server; every other id is silently dropped (as before). The web client does not offer or render external stickers yet.
* Migration `052_permission_bits.sql` keeps existing behaviour: roles and channel overwrites (allow and deny) holding `MANAGE_MESSAGES` get `PIN_MESSAGES`; those holding `MANAGE_MESSAGES` or `MANAGE_CHANNELS` get `BYPASS_SLOWMODE`; every @everyone role gets `USE_EXTERNAL_STICKERS` (also in `DEFAULT_EVERYONE`). Idempotent.

### Gradient role colours (053)
`Role.colorSecondary: number | null` (0..0xFFFFFF, second stop of a left-to-right gradient). `POST|PATCH /guilds/:id/roles[/:roleId]` accept `colorSecondary` (`null` clears). It needs a non-zero `color` (400 otherwise); setting `color: 0` clears the secondary; `@everyone` cannot have colours. `ROLE_CREATE|UPDATE` carry it. Web: the member's highest coloured role colours their name in messages and the member list (clipped gradient when a secondary colour exists).

### Welcome screen (054, community servers)
* Guild setting `PATCH /guilds/:id {community: boolean}` (MANAGE_GUILD) toggles the `COMMUNITY` feature; turning it on needs a rules channel (400 otherwise). Turning it off switches the welcome screen off (content kept).
* `Guild.welcomeScreen: {enabled, description<=300|null, channels:[{channelId, description 1-50, emoji|null}]} | null` (max 5 channels, `WELCOME_SCREEN_MAX_CHANNELS`). It is part of the guild object (`GUILD_CREATE`, `GET /guilds/:id`) and changes are broadcast with `GUILD_UPDATE`.
* `GET /guilds/:id/welcome-screen` (members) -> the screen (or an empty disabled one); `PATCH /guilds/:id/welcome-screen {enabled?, description?, channels?}` (MANAGE_GUILD, audit `GUILD_UPDATE`). 400 when the server is not a community, when a channel is missing, a category/thread, listed twice, **not visible to @everyone** (the screen is shown to every newcomer, so it must not reveal private channels), or when `enabled` with no channels.
* Web: Server Settings > Welcome Screen; newcomers see it in the welcome modal ("Start here" list with the managers' descriptions), also reachable later via "View Server Welcome". Servers using membership screening show the screening flow instead.

### Account deletion grace period (055) and ownership transfer
* `DELETE /users/@me {password, totp?}` no longer erases at once. After the usual checks (409 `OWNS_GUILDS` while owning servers) it sets `deletion_due_at = now + 14 days` (`ACCOUNT_DELETION_GRACE_DAYS`), revokes **all** sessions and push devices, disconnects the gateway, mails a notice and answers **202** `{deletionDueAt, graceDays}`. The account is otherwise untouched (others still see it) until the due date.
* **Logging in again before the due date cancels the deletion**: every path that mints a new session (password, passkey, QR/remote login, MFA) clears `deletion_due_at` and the auth response carries `deletionCancelled: true`. `DELETE /users/@me/deletion` clears it too (needs a session, i.e. a sign-in made during the grace period).
* The sweeper (`runSweeps`, step `account-deletions`) erases accounts past their due date exactly as the old immediate deletion did (anonymised "Deleted User", messages kept). If the account owns a server by then (created during the grace period) the server goes to its most senior human member (highest role position, then earliest join) or is deleted when nobody else is in it.
* `POST /guilds/:id/transfer-ownership {userId, password, totp?}` -> 204 (owner only; password and, with MFA, TOTP re-checked; the target must be a non-bot member; audit `GUILD_UPDATE {ownerId}`; broadcasts `GUILD_UPDATE`). The previous owner becomes a normal member.

### Already in place (verified in this pass, no change needed)
Server tags (`users.server_tag`, guild `tag`/`tagBadge`, `PATCH /users/@me {serverTagGuildId}`, shown in messages, member list and profile), message requests (`dm_participants.request`, `POST /channels/:id/accept-request|ignore-request`, `MESSAGE_REQUEST_UPDATE`, never rung: `ringableRecipients` skips `request`), and message forwarding (`POST /channels/:id/messages {forward:{channelId,messageId}}`: read access to the source, send access to the target, snapshot without author, forward chains keep the first origin).

### Audit taxonomy coverage
`apps/server/test/audit-coverage.test.ts` walks `AuditActionType`: every entry needs an `audit(...)` emitter in `apps/server/src` or an entry in the test's `RESERVED` map (with the reason); a reserved entry that gains an emitter fails the test until it is removed.

## Gap pass 2 (additive)
### Private and invitable threads, THREAD_LIST_SYNC
`POST /channels/:id/threads {name, type?: 'public'|'private' (default public), invitable?: boolean (private only, default true), autoArchiveDuration?}` starts a thread without a starter message (rate limit 10/min; parent must be a `text` channel, `announcement` for public only) -> 201 `Channel`. Public needs CREATE_PUBLIC_THREADS, private needs CREATE_PRIVATE_THREADS (not in the default @everyone set; grant per role/overwrite). The creator is the first member. `Channel.private` / `Channel.invitable` are present on private threads only.
A private thread is visible (channel fetch, messages, search, `GET /guilds/:id`, active/archived listings, gateway events, push) only to its members, its owner and holders of MANAGE_THREADS on the parent; everyone else gets 404. `PUT /channels/:id/thread-members/:userId` adds a person who can see the parent channel: on a private thread any member may when `invitable`, otherwise only the owner or MANAGE_THREADS. The invitee receives `THREAD_CREATE` (the thread appears) and leaving/removal sends them `THREAD_DELETE`.
Gateway `THREAD_LIST_SYNC {guildId, channelIds?, threads: Channel[], members: ThreadMember[]}` (GUILDS intent): sent after `READY` for each guild that has threads (whole guild, `channelIds` omitted) and when a user gains access to channels via overwrite/role changes (`channelIds` = the newly visible parents). Clients replace their known active threads in that scope with the payload. Migration 063 (`channels.thread_private`, `thread_invitable`).
### Role-restricted emoji
`Emoji.roleIds?: Id[]` (omitted when unrestricted). `POST /guilds/:id/emojis` accepts `roleIds` (<= 20 ids of this server's roles, @everyone rejected with 400) and `PATCH /guilds/:id/emojis/:emojiId` accepts `{name?, roleIds?}` (at least one; `roleIds: []` lifts the restriction). A restricted emoji can be used (in message content `<:name:id>` and as a reaction) only by members holding one of the roles or MANAGE_EMOJIS; otherwise 403 `EMOJI_RESTRICTED`. Deleting a role removes it from every emoji (and pushes `EMOJIS_UPDATE`). Clients hide emoji they cannot use from the picker. Migration 064 (`emojis.role_ids`).
### Group DM icon and ownership transfer
`PATCH /channels/:id` on a `group_dm` accepts `{name?: string|null, icon?: assetUrl|null, ownerId?: Id}` (strict). Any participant may change the name and icon; `ownerId` may only be set by the current owner (403 `NOT_OWNER` otherwise) and must name another participant (400). The owner is the only one who can remove other recipients, so a transfer moves that right. `Channel.icon` is present on group DMs (`null` = default glyph). Every participant receives `CHANNEL_UPDATE`. Migration 065 (`channels.icon`).
### User flags / badges
`User.publicFlags?: number` is a bitfield (`UserFlags` / `USER_BADGES` in `@jorcord/shared`: STAFF 1<<0, PARTNER 1<<1, BUG_HUNTER 1<<3, EARLY_SUPPORTER 1<<9, VERIFIED_BOT 1<<16, CERTIFIED_MODERATOR 1<<18, ACTIVE_DEVELOPER 1<<22). The super admin always carries STAFF. Only the instance super admin sets flags: `PATCH /admin/users/:id/flags {flags}` (unknown bits -> 400; 404 for everyone else; logged in the admin audit as `SET_USER_FLAGS`); the change is pushed as `USER_UPDATE` to everyone who can see the user. `GET /admin/users/:id` returns `publicFlags`. Profiles render the badges. Migration 066 (`users.public_flags`).
### Standard sticker packs
Original vector stickers shipped with every instance (`STANDARD_STICKER_PACKS` / `standardSticker()` in `@jorcord/shared`; ids `std_<slug>`, e.g. `std_gg`). `GET /stickers/standard` (public) -> `StandardStickerPack[] {id,name,description,stickers:[{id,packId,name,url,format:'svg'}]}`; each image is served publicly at `GET /stickers/standard/:id.svg` (`image/svg+xml`, immutable, `default-src 'none'; sandbox`). Message `stickerIds` accepts `std_*` ids (in addition to server sticker snowflakes) in servers and DMs; unknown ids are dropped like unknown server stickers. Clients render them from the catalogue.
### Desktop global push-to-talk
Tauri command `ptt_register {accelerator: string|null}` registers (or clears) one OS-wide push-to-talk hotkey (a `KeyboardEvent.code` such as `KeyV`/`Backquote`/`F5`, optionally with modifiers). The shell emits the window event `jorcord://ptt` with payload `true` on press and `false` on release. Only the web app's Voice settings ("Global push-to-talk", `prefs.pttGlobal`) use it; registration errors are ignored and the in-window key listener keeps working. `@jorcord/voice` `createPushToTalk` takes an optional `globalSource` (and a window blur no longer releases the key while one is set); `VoiceClient.setGlobalPttSource()` wires it.
### Friends "Active Now"
Web-only: the Friends home lists online friends that currently share an activity (rich presence from `PRESENCE_UPDATE.activities`), honouring each user's activity privacy as before. No new API.
